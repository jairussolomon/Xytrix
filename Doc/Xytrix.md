# 1. Introduction

Gate-Level Simulation (GLS) is the simulation of a synthesized gate-level netlist with or without timing information. It is performed after RTL synthesis or post place-and-route to verify whether the hardware implementation behaves correctly.

GLS validates that the functionality of the RTL design is preserved after synthesis and also checks whether timing delays affect the behavior of the circuit. According to the Cadence GLS guide, GLS remains an important verification step even with Static Timing Analysis (STA) and Equivalence Checking (EC) tools available. fileciteturn1file0L4-L5

# 3. Overview of Gate-Level Simulation

Gate-Level Simulation is performed using a gate-level netlist generated after synthesis.

The GLS flow generally includes:

| Input | Description |
|---|---|
| Gate-Level Netlist | Synthesized hardware description |
| Library Files | Standard cell timing and functional models |
| SDF File | Delay annotation file |
| Testbench | Used to verify functionality |

The GLS flow shown in the Cadence guide includes:

1. Netlist and SDF generation
2. GLS regression execution
3. Debugging failures
4. GLS signoff

The flowchart provided in the guide explains how timing failures are debugged and corrected iteratively before final signoff. fileciteturn1file0L11-L11

# 4. Why GLS is Important

GLS helps detect issues that cannot always be detected by STA or formal verification tools.

Important applications of GLS include:

| Purpose | Importance |
|---|---|
| Functional Verification | Confirms synthesized logic functionality |
| Reset Verification | Ensures proper initialization |
| Timing Verification | Detects setup/hold violations |
| DFT Verification | Verifies scan-chain insertion |
| Clock Tree Verification | Checks CTS implementation |
| Glitch Detection | Identifies transient timing issues |
| Power Verification | Verifies power-up behavior |

The Cadence document highlights that GLS is especially useful for asynchronous interface checking and post-layout verification. fileciteturn1file0L5-L5

# 5. Types of GLS

The Cadence guide categorizes GLS into three major types. fileciteturn1file0L6-L7

## 5.1 Zero Delay Simulation

Zero Delay Simulation ignores all timing information.

### Features

- No gate propagation delay
- SDF annotation ignored
- Faster simulation
- Mainly functional verification
- Used in early design stages

### Command

```bash
xrun -clean counter_netlist.v counter_test.v -mess -access +rwc -v slow_vdd1v0_basicCells.v -timescale 1ns/10ps -nospecify
```

The `-nospecify` switch disables timing information from specify blocks and ignores SDF annotation.

---

## 5.2 Unit Delay Simulation

Unit Delay Simulation assumes every gate has equal delay.

### Features

| Property | Description |
|---|---|
| Delay Type | Constant unit delay |
| Complexity | Lower than SDF simulation |
| Usage | Detect race conditions |
| Accuracy | Moderate |

This mode is useful for detecting genuine race conditions and timing-sensitive loops.

---

## 5.3 SDF Simulation

SDF Simulation is a timing-aware simulation where actual delays from the SDF file are annotated into the design.

### Features

| Property | Description |
|---|---|
| Timing Accuracy | High |
| SDF Annotation | Enabled |
| Timing Checks | Enabled |
| Runtime | Slower |
| Silicon Correlation | Very High |

### Command

```bash
xrun -v slow_vdd1v0_basicCells.v counter_netlist.v counter_test.v -mess -access +rwc -timescale 1ns/10ps -sdf_cmd_file sdf_cmd_file
```

The SDF file generated by synthesis or place-and-route tools is back-annotated into the netlist during elaboration. fileciteturn1file0L7-L8

# 6. Delay Models in GLS

The GLS guide describes two important delay models. fileciteturn1file0L9-L10

## 6.1 Transport Delay

Transport delay propagates every signal transition to the output.

### Characteristics

| Feature | Description |
|---|---|
| Glitch Filtering | No |
| Pulse Propagation | All pulses propagated |
| Usage | Interconnect modeling |
| Accuracy | Ideal wire behavior |

Transport delay is mainly used for modeling interconnects.

---

## 6.2 Inertial Delay

Inertial delay filters pulses smaller than the propagation delay.

### Characteristics

| Feature | Description |
|---|---|
| Glitch Filtering | Yes |
| Pulse Rejection | Small glitches removed |
| Usage | Gate modeling |
| Realism | More realistic |

The waveform illustration in the guide shows how inertial delay suppresses narrow pulses while transport delay propagates them. fileciteturn1file0L10-L10

Zero Delay GLS is useful for:

- Early functional verification
- Reset sequence checking
- DFT sanity checks
- Faster simulation turnaround

# 9. Comparison Between Zero Delay GLS and SDF GLS

| Feature | Zero Delay GLS | SDF GLS |
|---|---|---|
| Timing Annotation | Disabled | Enabled |
| Specify Block Delays | Ignored | Used |
| SDF File Usage | Ignored | Required |
| Simulation Speed | Faster | Slower |
| Functional Verification | Yes | Yes |
| Timing Verification | No | Yes |
| Setup/Hold Checks | Not Performed | Performed |
| Silicon Accuracy | Low | High |
| Glitch Detection | Limited | Accurate |
| Best Use Case | Early verification | Post-layout validation |

# 10. Common GLS Issues

The Cadence guide also discusses common issues encountered during GLS. fileciteturn1file0L20-L31

## Common Issues Summary

| Issue | Description |
|---|---|
| Zero Delay Loop | Infinite oscillation due to no delays |
| SDFNEP / SDFNET | Annotation mismatch errors |
| Timing Violations | Setup/hold failures |
| Glitch Suppression | Incorrect pulse handling |
| Delay Annotation Failure | Delays not reflected in waveform |

# 11. Example Timing Violation

Example warning from the guide:

```text
Warning! Timing violation
$setuphold<setup>
```

### Possible Causes

| Cause | Explanation |
|---|---|
| Setup Violation | Data arrived late |
| Hold Violation | Data changed too early |
| Annotation Problem | Delay mismatch |
| Incorrect Constraints | STA mismatch |

The guide recommends using `-sdf_verbose` and `-sdfstats` switches for debugging timing annotation failures. fileciteturn1file0L24-L25

# 12. Important GLS Switches

| Switch | Purpose |
|---|---|
| -nospecify | Disable timing information |
| -sdf_cmd_file | Specify SDF command file |
| -sdf_verbose | Detailed annotation logging |
| -gateloopwarn | Detect zero-delay loops |
| -notimingchecks | Disable timing checks |
| -pulse_r | Pulse rejection control |
| -pulse_e | Pulse error control |

These switches are useful for controlling timing behavior and debugging GLS runs. fileciteturn1file0L19-L20
